# Technical decisions

## Milestone 1

1. **Django 5.2 LTS and Python 3.13.** Keep the agreed Python-first foundation and a supported long-term Django line. Runtime packages are pinned in requirements files. [Django support](https://www.djangoproject.com/download/).
2. **DRF sessions and default authentication.** Browser and API share one origin in production; no token storage or CORS library is needed. Application login requires separate explicit CSRF handling next milestone. [DRF authentication](https://www.django-rest-framework.org/api-guide/authentication/).
3. **PostgreSQL 17 everywhere.** Use PostgreSQL for model constraints and tests, not a SQLite substitute. A dedicated local Docker container fills the missing native PostgreSQL installation; the production database remains managed PostgreSQL.
4. **Custom User before migrations.** Add the small admin/staff application role now so the project never needs to swap auth models later.
5. **python-dotenv for local configuration.** This small library loads an ignored environment file without a hand-written parser. Production uses exported environment variables and never reads local `.env` automatically.
6. **React/TypeScript/Vite with Tailwind's Vite plugin.** Strict types catch interface mistakes; a small component approach avoids a UI framework. React Router is deferred until real screens require routing. [Tailwind Vite setup](https://tailwindcss.com/docs/installation/using-vite).
7. **Database-aware readiness.** A server can be running while its database is unavailable. Return a minimal 503 rather than a misleading healthy response.
8. **Focused Django tests and Ruff now.** Database/permission/error tests protect this foundation. Playwright workflow automation waits for actual customer/staff flows. Browser smoke checks verify the current preview.

The dependency lockfile is generated by npm. Frontend type-package ranges are resolved by that lockfile; use `npm ci` to reproduce it. Review version upgrades deliberately.

Production hosting, static asset packaging, complete authorization, abuse protection, structured operational logs, reminders, and integrations are not complete at this milestone.

## Milestone 3 — 18 October 2026

- Lead mutations are named POST actions rather than broad record PATCHes. The service can validate each permitted transition, check ownership, and append its history in one transaction.
- Each action uses a client action UUID, a request fingerprint, and the lead version the user last read. PostgreSQL row locks serialize concurrent claims; same-key retries replay one result, changed payloads and stale versions return 409.
- Staff can read the team list to avoid hiding unassigned work, but can update only owned leads. Admin application role controls assignment and reopening; Django `is_staff` remains a separate technical permission.
- First contact has its own immutable-once timestamp. Stage, note, and integration activity do not stand in for a customer response.
- Quote values use SGD for this single-business MVP. Sales outcomes and closure reasons are recorded as structured lead state plus append-only activity.
- Manual inquiry receipt time must include a UTC offset and cannot be in the future. The interface captures it in Singapore time. Staff-created leads are owned by their creator; admin-created leads start unassigned.
- No services or runtime dependencies were added. Sessions, row locks, idempotency, team options, and workflow history use the existing Django/PostgreSQL stack.

## Milestone 2 — 18 October 2026

- React Router now supplies directly addressable inquiry, login, list, and detail pages. Prettier is a development-only formatter so the TypeScript/JSX remains readable. No other runtime services were added.
- Login uses Django's AuthenticationForm and session functions. Explicit `csrf_protect` on login/logout/intake also protects anonymous requests; a token bootstrap endpoint supports the SPA. Tokens are refreshed before writes to handle login rotation. [Django CSRF guidance](https://docs.djangoproject.com/en/5.2/howto/csrf/).
- Lead creation and its initial activity event commit together. A unique submission key handles races; the original normalized-payload hash decides safe replay versus conflict. No email or integration execution is created until the integration milestone.
- PostgreSQL row locks serialize shared rate counters. Fixed UTC windows limit public inquiry attempts (10/hour/IP) and login attempts (10/15 minutes/account; 30/15 minutes/IP). Only hashed subjects are stored. Expired counter cleanup will join scheduled maintenance in the background-work milestone.
- Forwarded IPs are ignored unless the immediate proxy is explicitly trusted. Production proxy configuration requires review against the actual ingress before launch.
- Backend development moves to 8001 because Docker already owns port 8000 here. Existing applications are left running.
- Local accounts have generated passwords in an ignored file; the helper is disabled for nonlocal databases and production. Public demo access/reset remains a later feature.
